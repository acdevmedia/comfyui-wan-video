# Video setup research and integration decisions

Research checked 13 November 2026. Model repository contents are pinned in each version profile; model quality and speed have not been measured on these bundles.

## Acceleration is already broader than Qwen

- **WAN 2.2 I2V-A14B:** the publisher supplies a matched high/low-noise [LightX2V four-step pair](https://huggingface.co/lightx2v/Wan2.2-Distill-Loras). The bundle uses its full rank-64 1022 release, strength 1 on each matching expert. The publisher's ComfyUI example (sigmas `[1, .9375001, .8333333, .625, 0]`, LoRA on both experts, CFG 1) produced visibly slow motion in GPU testing: frame-to-frame motion was ~60% of standard sampling. The turbo workflows therefore use the widely used three-stage schedule: 8 Euler/simple steps at shift 8, steps 0–2 on the high-noise base model without the LoRA at CFG 3.5 (negative prompt active), steps 2–4 high-noise with LoRA at CFG 1, steps 4–8 low-noise with LoRA at CFG 1. Measured on the same seed-free I2V test: ~94% of standard's motion in 47 s, against 25 s for LoRA-only and 176 s for standard (RTX PRO 6000). No Wan 2.1 or T2V adapter substitution. Rank-reduced [Banodoco conversions](https://huggingface.co/Banodoco/wan2.2-i2v-lightx2v-4step-loras) are candidates for later comparison, rather than assumed equivalent defaults.
- **MiniMax H3:** [Comfy-Org's packaging](https://huggingface.co/Comfy-Org/MiniMax-H3) now includes pruned-compatible FL2V four- and eight-step turbo adapters and a separate Ref2V adapter. The FL2VA pruned INT8 ConvRot base in this bundle uses the matching FL2V adapters; Ref2V weights are not interchangeable. Older [pruned Turbo conversions](https://huggingface.co/drbaph/MiniMax-H3-Turbo-Lora-ComfyUI) are useful provenance, but their release variants and projection dimensions must be checked before loading. Unpruned AdaLN adapters can have incompatible input dimensions. Use a converted pruned adapter, not merely a similarly named file.
- **10Eros-Max H3:** the [author's card](https://huggingface.co/TenStrip/10Eros-Max) distinguishes raw models and checkpoints with acceleration already merged. The bundle pins `beta7_fix1` native INT8 protected-edges HQ, with its baked eight-step turbo. It is a prerelease, not a claimed stable 1.0. The author recommends shift 12/3 with eight-step Euler/simple as a starting point for this family. Do not add the base H3 turbo adapter again. Earlier beta3/beta4 are described as corrupted tests; beta6 is discouraged. Beta7 variants have different attention, sparsity and flicker behavior: do not silently switch files while keeping a profile name.
- **WAN Remix v3:** the [author](https://huggingface.co/FX-FeiHou/wan2.2-Remix) distributes separate high/low I2V v3.0 FP8 files with acceleration and concept merges. No additional turbo LoRA is inserted. The repository's downloadable native example still names v0.6 and uses 12 steps, split 10, shift 8, CFG 1. This bundle uses those settings only as an explicitly experimental starting point for v3, not as a verified v3 recipe. The claim that Remix trades identity fidelity for natural motion is a working hypothesis to compare, not a guarantee supported by a controlled evaluation. The card also claims improved face consistency in later releases.
- **Qwen Edit 2511:** [LightX2V's project](https://github.com/ModelTC/LightX2V-Qwen-Image-Lightning) provides dedicated Lightning weights. The existing QWENEDIT-SETUP already pins both four- and eight-step 2511 BF16 LoRAs. Match the edit generation; Qwen Image, Edit 2509 and Edit 2511 are distinct adapter targets.
- **10Eros LTX 2.3:** the existing EROS-SETUP already pins [TenStrip's DMD hybrid v2](https://huggingface.co/TenStrip/LTX2.3_DMD_Lora). Its author's sigma lists and two-pass recipe should remain version-specific. This is a speed adapter too, even though it is not called Turbo.
- **Sulphur 2 / LTX 2.3:** the existing SULPHUR-SETUP includes both native-distilled weights and the author's conditioning-safe distillation adapter. The [author explicitly says](https://huggingface.co/SulphurAI/Sulphur-2-base) to choose the distilled checkpoint or dev plus distillation LoRA; do not combine both.
- **LTX 2.5:** [Lightricks publishes](https://huggingface.co/Lightricks/LTX-2.5) a native-distilled checkpoint and `ltx-2.5-22b-distilled-lora-450-bf16.safetensors` for dev-transformer workflows. LTX-SETUP already uses the distilled family. Do not reuse the 2.3 adapter on 2.5. The public card was discoverable, but direct raw-card access returned 401 in this session; file access may require the appropriate account/license.
- **Image bundles:** Z-Image Turbo, FLUX distilled/Klein variants and Ideogram Instant are accelerated checkpoints rather than universally compatible turbo LoRAs. Existing project profiles already distinguish those variants. [Hyper-FLUX.1-dev](https://huggingface.co/ByteDance/Hyper-SD) is an additional genuine eight-step adapter for FLUX.1 dev; it is not a FLUX.2/3 Klein adapter. No image-project model replacements were made in this task.

## Controls and prompt behavior

Every workflow uses the LTX/Eros canvas: 01 · Describe your shot (prompt), Starting image, 02 · Shot settings (width, height, duration in seconds, seed, H3 steps and CFG, prefilled editable negative prompt) and 03 · Your video. Frame count is derived from duration, not entered separately. WAN generates at 16 fps on a `4k+1` frame grid; H3 generates at 24 fps on `17k+5`. Duration rounds upward to a valid frame count, so 5 requested seconds is 81 frames / 5.0625s for WAN and 124 frames / 5.167s for H3. Dimensions are multiples of 32. Duration has no upper limit; only clips shorter than the 5-frame minimum are rejected (frames are never silently dropped and playback speed never changes). Wired lengths bypass the model nodes' own widget maxima, so long requests reach the sampler. H3's trained range is roughly 5–15 seconds and WAN's about 5 seconds: longer clips are untested for coherence, and time and VRAM grow faster than length (attention scales with the square of the token count).

Seeds use the seed extension shared with the LTX and Eros bundles (`web/seed-controls.js`): before every queue it writes a new random value (1 to 2^53-1, the widest range JavaScript holds exactly) into each seed widget whose seed mode is *randomize*, so the number shown is the one used; *fixed*, *increment* and *decrement* are also available. The backend node accepts the full 64-bit range; a value of 0 (the API graphs' default) draws a fresh `secrets.randbits(64)` seed on the server and re-executes every job (`IS_CHANGED=NaN`), while any non-zero value is deterministic, so fixing the seed reproduces a run. The seed is not an output of the Video controls node: ComfyUI cache keys include every ancestor's `IS_CHANGED`, so keeping it separate lets text encoding (the 32B Qwen3-VL encoder for H3) and reference-image encoding stay cached on re-rolls. Both WAN expert stages use the same seed and latent continuation.

At CFG 1 the sampler omits negative guidance. The negative field remains included and wired, but turbo/Remix workflows label this limitation. Raising CFG just to activate negatives changes distilled behavior and can add a second forward pass. WAN standard uses CFG 3.5 for negative guidance. H3 standard runs at CFG 1 (20 steps, res_multistep/simple), matching Comfy-Org's own H3 I2V template, which samples every path guidance-free with `BasicGuider`; this halves per-step compute versus the earlier CFG 6 proposal, and its negative is labelled inactive like the turbo modes. If H3 CFG is ever raised in the builder, its negative is encoded with `MiniMaxH3ImageToVideo` and the same reference image, because H3 keyframes and Qwen3-VL image tokens live in the conditioning; a text-only negative would leave the reference out of the unconditional pass and let CFG amplify the difference. Raising CFG on the CFGGuider in the UI alone keeps the text-only negative.

For I2V, start with **subject action, camera movement, environment response and motion timing**. Avoid spending the entire prompt describing static appearance already in the first frame. Keep one main action per short clip, state direction and speed concretely, and avoid mutually conflicting camera instructions. For H3, include desired audio/dialogue in the positive prompt. The [linked WAN prompting discussion](https://discuss.huggingface.co/t/how-to-get-the-most-out-of-prompts-for-wan-models/170354/2) and [Reddit thread](https://www.reddit.com/r/StableDiffusion/comments/1vprkrb/10eros_minimax_h3/) are useful anecdotal leads; the release/model sources determine the packaged filenames and sampling settings.

## Efficiency and reliability choices

1. Use native ComfyUI model nodes and a tiny local control/saver extension. Avoid making startup depend on mutable custom-node managers or automatically installing packages on every boot. Model files are revision-, size- and SHA256-pinned; the CUDA image is digest-pinned and ComfyUI is commit-pinned. Python transitive dependencies are resolved at image build and captured in `/opt/python-lock.txt`; they are not yet a fully frozen pre-build lock.
2. Use CUDA 13 and matching Torch/vision/audio wheels for H3 INT8 ConvRot as recommended by Comfy-Org. NVFP4 AWQ text encoding is supported outside Blackwell according to the packaging card; GPU/driver/kernel compatibility still needs a generation smoke test. PyTorch attention is the compatibility default. SageAttention 1.0.6 is pure Triton (no CUDA 12 binaries) and is installed for an opt-in `COMFYUI_ATTENTION=sage` experiment with a boot-time GPU check and PyTorch fallback.
3. Respect cgroup v2/v1 CPU quota and CPU affinity, preserve explicit OMP/MKL overrides, and avoid tokenizer/OpenBLAS/NumExpr oversubscription. This reduces CPU contention; it does not guarantee a particular GPU speedup.
4. Download only the selected model mode; `all` is optional. Lock shared-volume provisioning, resume Hub partial downloads, verify bytes (SHA256 once per file, then a stat-fingerprint record so warm boots on a network volume do not re-read ~40 GB), reserve 10 GB for outputs and stop on errors. Keep weights, input, output and user workflows under `/workspace/ComfyUI`. A persistent network volume is preferable for repeated deployments; a container disk alone does not survive Pod deletion.
5. Start with a 48 GB GPU and a five-second clip as a candidate configuration, not a validated minimum. H3 joint audio/video and its large text encoder may offload or need more VRAM. Use 80 GB for the first compatibility run if necessary, then measure 48 GB. Keep system RAM sufficient for text encoder and offloaded weights. Do not infer peak VRAM from the file sizes.
6. Compare FP8/INT8 results against higher precision before relying on appearance fidelity. Quantization reduces storage/residency but adapter application or dequantization can add temporary memory. Native model offloading remains enabled; no `--highvram` assumption is baked in.
7. Caches, compilation, sparse attention and `--fast` remain off by default (Sage and `--fast` are env opt-ins). The Eros card warns against cache/spectrum for reference fidelity and describes version-specific VSA requirements. Test VSA/Sage/TeaCache/compile as separately versioned experiments, measuring the first run and warm runs and checking identity/motion/audio. Four-step graphs offer little redundant denoising work for caches to skip.
8. Optional style/concept LoRAs should be added independently of acceleration. For WAN, target the correct expert pair and I2V architecture. For H3, check pruned/unpruned projection compatibility and FL2VA versus Ref2VA. The Eros author suggests lower concept strengths on some releases; 0.2–0.6 is a starting experiment from the card, not a blanket default for every LoRA. Do not claim that a LoRA loaded successfully merely because its file appeared in a dropdown.
9. A generation matrix must include PyTorch versus `COMFYUI_ATTENTION=sage` (and `COMFYUI_FAST=fp8_matrix_mult` for WAN) on identical seeds, H3 standard at CFG 1 against the Comfy-Org template output, warm re-roll time with an unchanged prompt, landscape/portrait, duration/frames, two successive randomized jobs, negative guidance on standard sampling, standard versus turbo, Remix versus standard reference identity, and H3 audio duration/synchronization. Also exercise restart preservation, interrupted downloads, disk-full handling and Runpod proxy navigation.

## Deployment gate

These repositories now have Git remotes, container build/publish automation, versioned release assets and Hub configuration. Current build results are recorded in VALIDATION.md. CPU installation/schema checks do not establish GPU generation quality or peak memory. Runpod Hub submission and public template publication are deferred until GPU tests pass. The Hub readiness check only verifies that ComfyUI starts after provisioning; it does not generate a video.
